# デスクトップアプリの Windows での確認手順

デスクトップアプリ（詳細設計 [`desktop-app.md`](desktop-app.md)、REVIEW_ISSUES No.49）を Windows の PC で動かし、CI では確かめられないこと（画面、WAM でのサインイン、Azure での計画 → デプロイ → 状態の確認 → 削除、Dry-run の保存）を確かめる手順です。

1. 準備（パッケージの取得と導入）……2 章
2. サインインせずに確かめる（Dry-run）……3 章
3. サインインして、Azure で確かめる……4・5 章
4. 後片付けと記録……6 章

- **所要時間**: 1 時間ほど（Environment の作成に 5〜15 分、削除に 10〜15 分かかります）
- **料金**: Container Apps（と、永続化を確かめる場合はストレージアカウント）の料金が少しかかります。最後に削除します
- **結果の記録先**: `docs/REVIEW_ISSUES.md` の No.49 と、詳細設計の「12. 実装フェーズ」の実施結果

## 1. この手順で使う言葉
| 言葉 | 意味 |
|---|---|
| [MSIX](https://learn.microsoft.com/ja-jp/windows/msix/overview) | Windows のアプリのパッケージの形式。Store からも、ファイルからも導入できる |
| [サイドロード](https://learn.microsoft.com/ja-jp/windows/application-management/sideload-apps-in-windows) | Store を通さずに、パッケージのファイルからアプリを導入すること。署名されたパッケージが必要 |
| [WAM](https://learn.microsoft.com/ja-jp/entra/msal/dotnet/acquiring-tokens/desktop-mobile/wam) | Windows の Web アカウント マネージャー。Windows にサインインしているアカウントで、Azure にサインインできる |
| 計画 | アプリは、Azure を変更する前に、読み取りだけで計画を作り、利用者が確かめてから実行する（CLI の `--dry-run`、MCP の `plan_*` と同じ） |

## 2. 準備
### 2.1 使うもの
- [ ] Windows 10（1809 以降）または Windows 11 の PC（x64 または arm64）
- [ ] 確認に使う Azure のサブスクリプションと、そこで Contributor 以上のロールを持つアカウント（[README の必要な RBAC ロールと権限](../../README.md)）。MFA を登録してあること（Azure の作成・削除には MFA が必須）
- [ ] リソースプロバイダー `Microsoft.App`（と、永続化を確かめる場合は `Microsoft.Storage`）が登録されている
- [ ] （Dry-run の起動の確認をする場合）Docker Desktop

### 2.2 パッケージを取得する
CI（`ci.yml` の `desktop` ジョブ）の成果物 `ttdeploytool-desktop-msixupload`、またはリリースの `ttdeploytool-desktop-vX.Y.Z.msixupload` を取得します。

`.msixupload` と中の `.msixbundle` は zip の形式です。拡張子を `.zip` に変えて展開すると、`.msixbundle` が、さらに展開すると x64 と arm64 の `.msix` が出てきます。

### 2.3 導入する
Store の限定公開で導入できる場合は、Store から導入します（この場合 2.2 は不要）。Store を使わない場合は、次のどちらかでサイドロードします。CI とリリースのパッケージは署名されていないため、署名か開発者モードが必要です。

- **開発者モード + Visual Studio**: リポジトリを取得し、`TTDeployTool.Desktop.slnx` を Visual Studio で開き、`TTDeployTool.Controller.Desktop` をスタートアップ プロジェクトにして、プラットフォーム `x64`（Arm の PC は `ARM64`）・起動プロファイル「TTDeployTool.Controller.Desktop (Package)」で実行する（[WinUI 3 の開発環境](https://learn.microsoft.com/ja-jp/windows/apps/get-started/start-here)。Windows の「設定」→「システム」→「開発者向け」で開発者モードを有効にする）
- **自己署名の証明書で署名して導入**: [自己署名の証明書を作り](https://learn.microsoft.com/ja-jp/windows/msix/package/create-certificate-package-signing)、`.msix`（x64 または arm64）に [SignTool で署名](https://learn.microsoft.com/ja-jp/windows/msix/package/sign-app-package-using-signtool)し、証明書を「信頼されたユーザー」に入れてから、`.msix` を開いて導入する。証明書の発行者（`CN=...`）は、マニフェストの `Publisher`（CI のパッケージは `CN=TTDeployTool`）と同じにする

## 3. サインインせずに確かめる
| # | 操作 | 確かめること |
|---|---|---|
| 1 | アプリを起動する | 「サインインと対象」が表示される。「サインインしていません（Dry-run はサインインせずに使えます）」と表示される。Store 以外から導入した場合、「更新があります」は表示されない |
| 2 | 「設定」を開く | 誤りの欄に subscription・resource-group・2 つのパスワードの不足が表示される。CPU とメモリの既定値（1.5 / 3.0 / 1.0 / 2.0 / 0.5 / 1.0） |
| 3 | DB 種別を `sqlserver` にする | タグの欄の薄い文字（既定のタグ）が `-mssql` のタグに変わる。警告に「Azure 上の SQL Server 構成ではサンプル DB を作成できません」 |
| 4 | Timetracker のメモリを `1,5` にする | 誤りに「tt-memory には数値を指定してください（小数点は「.」）」。`2` にすると、誤りが消えて OutOfMemory の警告が出る |
| 5 | DB 種別を `postgresql`、メモリを `3.0` に戻し、2 つのパスワード（8 文字以上）を入れる | パスワードは伏せ字で表示される |
| 6 | 「ローカル検証（Dry-run）」で「保存先を選んで保存」を押し、空のフォルダーを選ぶ | `.env` の注意が表示されている。保存の後、次の手順が 3 つと docker-compose.yml の内容が表示される。docker-compose.yml にパスワードが含まれない |
| 7 | 同じフォルダーにもう一度保存する | 上書きの確認が出る。「キャンセル」なら上書きしない。「上書きする」なら上書きする |
| 8 | 「フォルダーを開く」を押す | エクスプローラーで保存したフォルダーが開く |
| 9 | （Docker Desktop がある場合）保存したフォルダーで `docker compose up -d` を実行し、`http://localhost:8080` を開く | Timetracker のセットアップの画面が表示される。確かめたら `docker compose down -v` |
| 10 | 「設定」で DB のデータを「Azure Files に永続化する」にし、Dry-run で保存する | 警告に「persist-db は Azure 向けの設定のため、ローカル（Dry-run）では使いません」 |

## 4. サインインして確かめる
| # | 操作 | 確かめること |
|---|---|---|
| 1 | 「サインイン」を押す | WAM のアカウントの選択（または Windows のアカウントでのサインイン）が表示される。サインインすると、アカウント名が表示され、「サインイン」が押せなくなり、「サインアウト」が押せるようになる |
| 2 | サインインの後 | サブスクリプションの一覧に、入れるテナントのサブスクリプションが「名前（ID、テナント名）」で並ぶ。読めないテナントがあれば、その旨が一覧の下に出る（ほかのテナントの一覧は出る）。サブスクリプションが 1 つなら選ばれている |
| 3 | アプリを閉じて、もう一度起動する | 対話なしでサインインした状態に戻り、サブスクリプションが読まれる |
| 4 | 「サインアウト」を押し、アプリを再起動する | サインインしていない状態で始まる。もう一度「サインイン」する |
| 5 | サインインの画面を閉じる（キャンセル） | エラーは表示されない |

## 5. Azure で確かめる
確認用のリソースグループ名を決めます（例: `rg-tt-desktop-check`。無ければアプリが作ります）。アプリ名は `ttdesk` などにします。

| # | 操作 | 確かめること |
|---|---|---|
| 1 | 「サインインと対象」でサブスクリプション・リソースグループ・アプリ名を入れ、「設定」でパスワードを入れて、「デプロイ」で「計画」を押す | 操作の一覧（リソースグループ・Environment・3 つの Container App の「作成する」）、DB のデータの永続化（「永続化しない」）、権限（リソースグループが無い場合は「確認できませんでした」）、所要時間、計画の有効期限が表示される |
| 2 | 「実行」を押す | 実行中の表示（進み具合のバー、「1 / 3: リソースグループ ...」などの手順、ログ）が更新される。実行中にウィンドウを閉じようとすると確認が出る（「キャンセル」で閉じない） |
| 3 | 完了を待つ | 「完了」と Timetracker の URL が表示される。「Timetracker を開く」でブラウザーが開き、セットアップの画面に転送される |
| 4 | 「状態の確認」で「読み込む」を押す | Environment と 3 つのアプリの状態（Succeeded / Running）、CPU とメモリ、イメージ、URL、「DB のデータ: 永続化していません」 |
| 5 | 「デプロイ」で、もう一度「計画」を押す | DB アプリが「更新する（DB のデータが失われるおそれがあります）」になり、同意のチェックが表示される。チェックを入れるまで「実行」を押せない。チェックを入れて実行し、完了する |
| 6 | 計画を作った後、「サインインと対象」のアプリ名を変える | 「デプロイ」の計画が消える（計画と違う内容で実行しない） |
| 7 | 計画を作り、15 分待ってから「実行」を押す | 計画の有効期限が切れた旨が表示され、実行しない |
| 8 | 「削除」で「計画」を押す | 4 つ（と、ストレージアカウントの行）が表示され、「DB アプリを削除すると DB のデータはすべて失われます」、リソースグループは削除しない旨が出る。アプリ名を違う値で入れると「削除」を押せず、計画のアプリ名を入れると押せる |
| 9 | 「削除」を押す | 実行中の表示の後、「完了」と、削除したもの・既に無かったもの・残したリソースグループが表示される（Environment の削除に 10〜15 分） |
| 10 | 「状態の確認」で「読み込む」を押す | 「デプロイされた環境はありません。」 |

永続化を確かめる場合（任意。[DB データの永続化の詳細設計](db-persistence.md)）:
| # | 操作 | 確かめること |
|---|---|---|
| 11 | 「設定」の DB のデータを「Azure Files に永続化する」にして計画 → 実行する | 計画にストレージアカウント・ファイル共有・Environment のストレージの作成と、料金の案内が出る。完了の後、DB のデータの保存先（ストレージアカウント）が表示される |
| 12 | 「今の状態を引き継ぐ」に戻して、もう一度計画する | 「DB のデータ: Azure Files に永続化する」になり、同意のチェックは出ない（停止して更新する旨の警告が出る） |
| 13 | 「削除」で「DB のデータを残す」にチェックを入れて計画 → 削除する | ストレージアカウントが「削除しない」（「DB のデータを残す」の指定により残します）になり、残すもの・料金がかかり続けることが表示される。完了のログにも同じ案内が出る |
| 14 | もう一度、チェックを外して計画 → 削除する | ストレージアカウントも削除する旨の警告が出て、削除される |

## 6. 後片付けと記録
- [ ] 「状態の確認」で、デプロイされた環境が無いことを確かめる
- [ ] 確認用に作ったリソースグループを削除する（`az group delete --name <リソースグループ名>`）
- [ ] 2.3 で自己署名の証明書を入れた場合は、「信頼されたユーザー」から削除する
- [ ] 結果（確かめたこと、見つかった問題）を `docs/REVIEW_ISSUES.md` の No.49 と、詳細設計の 12 に記入する。詳細設計の「11. 確認事項」のうち確かめられたもの（2 のトークンのキャッシュの保存先、3 のジョブの途中の MFA、4 の複数のテナント、5 の Store の更新の確認）も記入する

## 7. うまくいかないとき
| 症状 | 考えられる原因 |
|---|---|
| `.msix` を開いても導入できない（署名が無い・信頼されていない） | 2.3 の署名と証明書の信頼が必要。証明書の発行者がマニフェストの `Publisher` と違う |
| サインインでエラーになる（`AADSTS50011` など、リダイレクト URI の不一致） | アプリ登録のリダイレクト URI に `ms-appx-web://Microsoft.AAD.BrokerPlugin/<クライアント ID>` が無い（[提出手順](desktop-app-store.md)の 2 章）。クライアント ID を渡さずにビルドした場合は、Azure.Identity の既定（開発用）を使う |
| 実行で「多要素認証（MFA）が必要です」と表示される | MFA を行わずにサインインした。サインインし直し、MFA を行う（詳細設計 5.3） |
| 計画で権限が不足している | アカウントに Contributor 以上のロールが無い（README の必要な RBAC ロールと権限） |
| サブスクリプションが一覧に出ない | そのテナントで MFA などのため読めない（一覧の下の注意を確かめる）。サインインし直すと読める場合がある |
