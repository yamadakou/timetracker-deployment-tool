# 詳細設計: デスクトップアプリの画面の流れ（デプロイのウィザード・一覧からの削除・実行状況）（Phase 7f）

- 対象ブランチ: `feature/desktop-app`
- 状況: 論点はオーナーの回答で決めた（5）。2026-10-22
- 記録: `docs/REVIEW_ISSUES.md` の No.59

## 1. 目的
オーナーの実機での確認（2026-10-22）で、次の要望があった。

1. 左のメニューから「削除」を無くし、削除の画面はデプロイの一覧からだけ開く
2. 左のメニューから「デプロイ」を無くし、設定 → デプロイをウィザードにして、最後に「今すぐ実行」か「予定に追加」を行う。画面の数を増やしてよいので、項目の並びと順序を見直す。設定の Markdown のコピーはウィザードのどの画面にも出し、ウィザードのすべての画面の入力をコピーする。必須の入力が無い・入力に誤りがある場合は、次の画面に進めない
3. 「状態の確認」はデプロイか削除を実行した後にしか使わないため、メニューから無くし、ウィザードの「今すぐ実行」と、一覧からの削除の実行の後に表示する
4. デプロイの一覧はサインインしないと使えないため、サインインするまで押せないようにする

## 2. 画面の構成
左のメニュー:

| 項目 | 内容 |
|---|---|
| サインイン | サインイン・サインアウト、読めなかったテナントの注意 |
| デプロイの一覧 | 7d-2 のとおり。サインインするまで押せない |
| 新しくデプロイ | ウィザード（3） |
| ローカル検証（Dry-run） | DB 種別・DB 名・タグ・パスワードの入力（ウィザードと同じ値）と保存 |
| ジョブ | ジョブの一覧、同時に実行する数（「設定」から移す）、診断用のログ |

メニューに出さない画面:

| 画面 | 開くところ |
|---|---|
| 削除 | 一覧の行の「削除」（開くと計画を作る） |
| 実行状況 | ウィザードの「今すぐ実行」・削除の画面の「今すぐ削除」の後と、一覧の行の「状態を確認」 |

- 「予定に追加」の後は、ジョブの画面を開く
- 実行状況の画面: 対象のジョブ（実行中・終わったもの）の進み具合とログ、その下に Azure の状態（今の「状態の確認」）。ジョブが終わったら、Azure の状態を読み直す。一覧の行から開いた場合は、その対象の最も新しいジョブ（無ければ状態だけ）
- 削除の画面と実行状況の画面には「デプロイの一覧に戻る」を置く

## 3. デプロイのウィザード（オーナーの回答: 5 画面）
| 画面 | 項目 | 次に進む条件（誤りが無いこと） |
|---|---|---|
| ① 対象 | テンプレートから入力、サブスクリプション、リソースグループ、アプリ名、リージョン | サブスクリプション・リソースグループ・アプリ名 |
| ② DB | DB 種別、DB 名、Timetracker のイメージのタグ、DB のデータの永続化 | DB 種別・タグ（DB 種別との組み合わせ） |
| ③ パスワード | DB のパスワード、Timetracker のパスワード | パスワード（SQL Server の要件を含む） |
| ④ スペックと利用可能期限 | 3 つのコンテナの CPU とメモリ、利用可能期限日 | CPU とメモリ・期限日 |
| ⑤ 確認と実行 | 入力の一覧、計画（開くと作る）、DB のデータが失われることへの同意、テンプレートとして保存、今すぐ実行・予定に追加 | — |

- どの画面にも出すもの: 何番目の画面か、「戻る」「次へ」、「Markdown でコピー」と「パスワードも含める」（①〜④のすべての入力をコピーする。7e のとおり）、「初期値に戻す」
- 誤りは、その誤りの項目がある画面に出す（検証の規則とメッセージは CLI・MCP と同じ `DeploymentValidator` のまま。メッセージの先頭の項目名で画面を決める）。警告も同じ（どの画面とも決まらない警告は ⑤ に出す）。⑤ には、すべての誤りと警告を出す
- 「次へ」は、その画面と前の画面に誤りがあれば押せない。誤りのある画面の「次へ」の横に、誤りの数を出す
- 計画は ⑤ を開いたときに作る（入力を変えると計画は消え、⑤ を開き直すと作り直す）
- サブスクリプション（オーナーの判断、2026-10-22）: ウィザードの ① で選ぶ。デプロイの一覧は選択によらず、読めるすべてのサブスクリプションを読む。一覧のサブスクリプションの絞り込みは、文字の入力から「すべて」＋サブスクリプションのドロップダウンに変える

## 4. テスト
- `Desktop.Core`: ウィザードの各画面の「次へ」の条件、誤りと警告の振り分け、⑤ で計画を作ること、今すぐ実行で実行状況へ・予定に追加でジョブへ移ること、一覧の削除で削除の画面を開いて計画すること、今すぐ削除で実行状況へ移ること、実行状況のジョブと読み直し、一覧のサブスクリプションの絞り込み、サインインの前は一覧を使えないこと。分岐網羅率 100%
- UI テスト（CI）: メニューの項目、一覧がサインインの前に押せないこと、ウィザードの「次へ」が誤りで押せないこと、Markdown のコピーのボタンがどの画面にもあること
- UI テスト（Azure）: ウィザードでデプロイ → 実行状況、一覧の削除 → 削除の画面 → 実行状況の流れに書き直す

## 5. 実施結果
- Desktop.Core: `DeployWizardViewModel`（画面・誤りと警告の振り分け・「次へ」の条件・⑤ で計画）、`MainViewModel.OpenAsync`（wizard・status・delete）と `StatusJob`（実行状況のジョブ。終わると Azure の状態を読み直す）、今すぐ実行・今すぐ削除の後は実行状況、予定に追加の後はジョブの画面。一覧のサブスクリプションの絞り込みのドロップダウン（読み直しても選んだものを残す）
- 画面: メニュー（サインイン・デプロイの一覧・新しくデプロイ・ローカル検証・ジョブ）、ウィザードの 5 画面、実行状況（ジョブの進み具合・Timetracker を開く・Azure の状態）、削除と実行状況の「デプロイの一覧に戻る」、Dry-run の DB とパスワードの入力、ジョブの画面の同時に実行する数
- テスト: `Desktop.Core` 212 件成功・行と分岐の網羅率 100%。ジョブの終わりを待つテスト用の処理（`JobQueue.WhenIdleAsync`）が、状態が変わってから終わりの通知までの間に戻ることがあり、通知のテストがまれに失敗したため、終わったジョブも通知の後に完了するものを待つようにした（6 回続けて成功）
- UI テスト（CI）: サインインしないとウィザードの ① から進めないため、テンプレートの保存と ④ の検証の CI の UI テストは外し（単体テストで確かめる）、Azure の UI テストに、ウィザードの全画面・テンプレートの保存・実行状況・一覧の削除の流れを入れた

- Desktop System Test（run 39800437539）で、⑤ でテンプレートの名前を入れて保存すると、デプロイの計画が消えて「今すぐ実行」が無くなった。デプロイの ViewModel が、設定の ViewModel のすべてのプロパティの変更で計画を消していたため。デプロイの入力が変わったときの通知（`SettingsViewModel.InputChanged`）だけで消すように直した

- 再実行の Desktop System Test（run 39914420298）で、デプロイの直後に一覧を読むと、Resource Graph に Timetracker のアプリがまだ無く、行が「一部だけ」になって「パスワードを表示」が押せなかった。このアプリで終えたデプロイの結果を重ねるときに、一部だけ反映されている行の無いもの（Container App・Environment・ストレージアカウント）を結果で補うようにした（desktop-jobs.md の 6.4 の「反映の遅れ」の補い方を、行が既にある場合にも広げた）

- 直した後の Desktop System Test（run 39915938372）で、ウィザード → 実行状況 → 一覧（パスワード・期限の変更）→ 一覧からの削除 → 実行状況の流れと、これまでの確認（同じ対象の計画の拒否・予定・常駐・同時実行・停止・リソースグループの削除）が成功した
