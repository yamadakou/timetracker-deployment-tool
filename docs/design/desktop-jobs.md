- 対象ブランチ: `feature/desktop-app`
- 前の段階: `docs/design/desktop-app.md`（Phase 5）、`docs/design/desktop-ui-tests.md`（Phase 6）
- 状況: 案。オーナーの回答で決めたこと（7）と、まだ決めていないこと（8）がある。一次情報の確認日は 2026-10-20
- 記録: `docs/REVIEW_ISSUES.md` の No.52（予定）

## 1. 目的
オーナーの Windows の実機での確認（2026-10-20）で、次の問題が見つかった。
| # | 問題 | 原因 |
|---|---|---|
| P1 | 計画し直すと、エラーの表示領域（赤い枠）だけが残り、メッセージは消える。エラーの表示 6 か所に共通 | 表示の切り替えを `x:Bind` の関数（`Ui.IfText(Error)`）で行っている。メッセージ（`Message`）は消えるのに表示が残るため、引数が null に戻ったときに関数が呼び直されていないと見込む（Microsoft Learn の関数の結び付けの説明には、引数が null の場合の記載が無い。7a で、直した版と直す前の版を実機・UI テストで比べて確かめる） |
| P2 | デプロイの途中で「状態の確認」をすると「デプロイされた環境はありません。」と「DB のデータ: 永続化していません」が表示される（永続化してデプロイしたのに） | 実行中で、まだ Environment とアプリが無かった。環境が無い場合にも、永続化の行に既定の文を出していた |
| P3 | ボタンを押した後の表示が遅く、止まっているのか動いているのか分からない（状態の確認で数十秒、何も表示されない） | 処理中であることを、ボタンを押せなくすることでしか示していない。Azure を順に読む段階を知らせていない |
| P4 | 削除を実行すると、デプロイの画面に削除の進み具合が表示される。削除中にも「Timetracker を開く」が押せる | 画面は「最後に始めたジョブ」を 1 つだけ持ち、デプロイ・削除の両方の画面に表示している。ボタンの有効・無効を、ジョブが変わったときに更新していない |
| P5 | 処理中に別の画面に移れ、実行中にも計画・対象の変更・別の対象の実行ができる | 同じ対象のジョブは、実行の段階で Application のジョブの管理が拒否する（`WorkflowFailure.Conflict`）が、画面では止めていない。対象が違えば同時に実行できるが、画面には 1 つしか出ない |

あわせて、オーナーの依頼で、対象が違うデプロイ・削除を同時に実行・順番待ちにでき、ジョブの状況を一覧で確かめ、待機中・予定のジョブを取り消し・一時停止でき、予定の時刻に実行できるようにする。ジョブがある間は、ウィンドウを閉じても通知領域に常駐して続ける。

## 3. P1〜P4 の修正（7a）
### 3.1 エラーの表示（P1）
- `Visibility` を関数の結び付けではなく、ViewModel の `bool`（例: `HasError`。`Error` が変わるたびに変更を通知する）で決める。引数が null になる関数の結び付けを使わないため、原因の見込みが外れていても直る
- 同じ作りの表示（`IfText` / `IfNotNull` を使うもの: エラー 6 か所、Dry-run の docker-compose.yml、URL、削除のアプリ名の入力欄）をすべて直す
- UI テスト（CI）: Dry-run で誤った設定で保存してエラーを出し、正しい設定にして保存すると、エラーの領域が消える

### 3.2 状態の確認（P2）
- 環境が無い（`Exists` が false）場合は、永続化の行を出さない（「デプロイされた環境はありません。」だけにする）
- 同じ対象のジョブが実行中・待機中なら、「デプロイ（または削除）を実行中のため、まだ反映されていない場合があります」と添える

### 3.3 処理中の表示（P3）
- 計画（デプロイ・削除）、状態の確認、サブスクリプションの読み込み、Dry-run の保存の各画面に、処理中の表示（`ProgressRing`）と、今している段階の文、経過した秒数を出す
- 段階は Application から知らせる。`DeploymentWorkflow.PlanAsync` / `DeletionWorkflow.PlanAsync` / `DeploymentInspector.InspectAsync` に、省略できる `IProgress<string>`（段階の説明）を足す（CLI・MCP は渡さないので、動きは変わらない）。段階の例:
  | 処理 | 段階 |
  |---|---|
  | デプロイの計画 | リソースグループを確認しています → Container Apps Environment を確認しています → Container Apps を読んでいます → ストレージアカウントを確認しています（永続化する場合） → 権限を確認しています |
  | 削除の計画 | リソースグループを確認しています → 削除の対象を読んでいます → ストレージアカウントを確認しています |
  | 状態の確認 | リソースグループ → Environment → Container Apps → ストレージアカウント |
  | サブスクリプションの読み込み | テナントの一覧を読んでいます → テナント n / m（名前）のサブスクリプションを読んでいます |
- 実行中のジョブは、今と同じく手順（「2 / 4: …」）と進み具合のバーを出す。7b の帯（4.4）で、どの画面からも分かるようにする

### 3.4 デプロイ・削除の画面のジョブ（P4）
- デプロイの画面には、その対象の直近のデプロイのジョブだけを、削除の画面には直近の削除のジョブだけを出す（7b ではジョブの一覧から選んだものを詳しく出す）
- 「Timetracker を開く」は、直近のデプロイが成功して URL がある場合だけ押せる。ジョブが変わるたびに押せるかを更新する

## 4. ジョブの順番待ち・予定・停止（7b）
### 4.1 ジョブの状態
| 状態 | 意味 | できる操作 |
|---|---|---|
| 予定 | 指定の時刻まで待つ | 取り消し、一時停止、時刻の変更 |
| 待機中 | 同時実行の上限に達しているため、順番を待つ | 取り消し、一時停止 |
| 一時停止 | 利用者が止めた（予定・待機中から）。再開するまで実行しない | 再開（予定の時刻を過ぎていれば待機中になる）、取り消し |
| 実行中 | Azure を操作している | 停止（今の手順の後で止める） |
| 停止中 | 停止を受け付け、今の手順が終わるのを待っている | なし |
| 完了 / 失敗 / 取り消し / 停止 | 終わった | 詳細の表示、記録から消す |

### 4.2 登録
- 計画 → 確認（今と同じ）の後、「今すぐ実行」か「予定に追加（日時）」を選ぶ。今すぐ実行でも、同時実行の上限に達していれば待機中になる
- 同じ対象（サブスクリプション・リソースグループ・アプリ名）のジョブが予定・待機中・一時停止・実行中・停止中なら、その対象は計画も登録もできない（D2。画面に「この対象のジョブ（予定 10:30）があるため、計画できません」などと出す）
- 計画の有効期限（15 分）より後に実行するジョブは、実行の直前に計画し直し、利用者が確かめた計画と比べる（操作の一覧、データ消失の同意が要るか、ブロッカー、作るストレージアカウント）。違えば実行せずに失敗にし、理由（何が変わったか）を出す。同じ対象のジョブは登録させないため、違いは本ツールの外での変更か、別の PC・CLI・MCP からの操作による
- デプロイのジョブはパスワードを含む設定を持つ。アプリの中（メモリ）だけに持ち、保存しない

### 4.3 実行
- 対象が違うジョブは同時に実行する。同時に実行する数の上限は既定 2（「設定」で 1〜4。この値はアプリのデータに保存する）（D1）
- 予定の時刻を過ぎたもの・待機中のものから、登録の順に始める
- 停止（D4）: ジョブの各手順の境目（`JobContext.ReportStep`）で停止の要求を確かめ、要求があれば次の手順に進まずに「停止」で終える。今の手順（例: Environment の作成。10 分前後かかる）は止めない。作りかけのリソースは残り、もう一度実行すると続きから処理する（デプロイは冪等）。削除で止めた場合も、もう一度削除すれば続きから消す
- Application の変更: `JobContext` に停止の要求（`StopRequested`）と、`JobStatus.Stopped` を足す。MCP は停止を要求しないため、MCP のジョブは今と同じ（`get_job_status` の状態に `stopped` が出ることはない）

### 4.4 画面
- 「実行の記録」を「ジョブ」に改め、すべてのジョブを一覧にする（種別、対象、状態、予定の時刻、手順、経過時間、操作のボタン）。選んだジョブのログと結果を下に出す
- どの画面にも、上部に帯を出す（例: 「実行中 1・待機中 1・予定 2」。押すとジョブの画面に移る）
- 実行中でも、別の対象の計画・登録、状態の確認、Dry-run はできる

### 4.5 Azure へのサインイン
- 予定の時刻にトークンの取得で対話（MFA など）が要る場合は、WAM のサインインの画面が出る。サインインしないまま一定時間（10 分）が過ぎたら、そのジョブは失敗にし、通知する（ほかのジョブは続ける）

## 5. 通知領域への常駐（7c）
- ジョブ（予定・待機中・一時停止・実行中・停止中）があるときにウィンドウを閉じると、アプリを終了せず、ウィンドウを隠して通知領域にアイコンを出す（D3。オーナーの提案）。初めて隠したときに「バックグラウンドで実行を続けています」と通知する
- 通知領域のアイコンのメニュー: 「開く」「終了」。「終了」は、ジョブが残っていれば確認する（実行中のジョブは止まり、作りかけのリソースが残る。予定・待機中のジョブは消える）
- ジョブが終わる（完了・失敗・停止）たびに通知し、通知を押すとそのジョブを開く（Windows App SDK の `AppNotificationManager`）
- ジョブが無いときにウィンドウを閉じると、今と同じく終了する
- 制約（画面と手順書に書く）: Windows のサインアウト・再起動・シャットダウンではアプリが終わり、残ったジョブは消える。PC がスリープしている間は実行しない（予定の時刻に寝ていた場合は 8 の Q2）
- 通知領域のアイコンは、WinUI 3 と Windows App SDK に API が無いため、Win32 の `Shell_NotifyIcon` を使う。OSS の H.NotifyIcon.WinUI（2.4.1）を使うか、小さな相互運用のコードを自分で書くかは 8 の Q3

## 6. テスト
- `Desktop.Core`: ジョブの予定・待機・一時停止・取り消し・停止・同時実行の上限・同じ対象の拒否・計画し直しての比較（違えば失敗）を、偽の時刻（`TimeProvider`）と偽の Azure で確かめる。分岐網羅率 100%
- Application: `IProgress<string>` を渡したときに段階が順に届くこと、渡さないときに今と同じこと。停止の要求で次の手順に進まないこと（MCP の既存のテストはそのまま通る）
- UI テスト（CI）: P1（エラーの領域が消える）、処理中の表示が出て消えること（Dry-run の保存）、ジョブの画面と帯の表示（ジョブが無い状態）
- UI テスト（半自動。Azure）: 2 つの対象を登録し、同時に実行されること、同じ対象を計画できないこと、予定の取り消し、停止
