## 1. 目的
オーナーの Windows の実機での確認（2026-10-20）で、次の問題が見つかった。
| # | 問題 | 原因 |
|---|---|---|
| P1 | 計画し直すと、エラーの表示領域（赤い枠）だけが残り、メッセージは消える。エラーの表示 6 か所に共通 | 表示の切り替えを `x:Bind` の関数（`Ui.IfText(Error)`）で行っている。メッセージ（`Message`）は消えるのに表示が残るため、引数が null に戻ったときに関数が呼び直されていないと見込む（Microsoft Learn の関数の結び付けの説明には、引数が null の場合の記載が無い。7a で、直した版と直す前の版を実機・UI テストで比べて確かめる） |
| P2 | デプロイの途中で「状態の確認」をすると「デプロイされた環境はありません。」と「DB のデータ: 永続化していません」が表示される（永続化してデプロイしたのに） | 実行中で、まだ Environment とアプリが無かった。環境が無い場合にも、永続化の行に既定の文を出していた |
| P3 | ボタンを押した後の表示が遅く、止まっているのか動いているのか分からない（状態の確認で数十秒、何も表示されない） | 処理中であることを、ボタンを押せなくすることでしか示していない。Azure を順に読む段階を知らせていない |
| P4 | 削除を実行すると、デプロイの画面に削除の進み具合が表示される。削除中にも「Timetracker を開く」が押せる | 画面は「最後に始めたジョブ」を 1 つだけ持ち、デプロイ・削除の両方の画面に表示している。ボタンの有効・無効を、ジョブが変わったときに更新していない |
| P5 | 処理中に別の画面に移れ、実行中にも計画・対象の変更・別の対象の実行ができる | 同じ対象のジョブは、実行の段階で Application のジョブの管理が拒否する（`WorkflowFailure.Conflict`）が、画面では止めていない。対象が違えば同時に実行できるが、画面には 1 つしか出ない |

あわせて、オーナーの依頼で、対象が違うデプロイ・削除を同時に実行・順番待ちにでき、ジョブの状況を一覧で確かめ、待機中・予定のジョブを取り消し・一時停止でき、予定の時刻に実行できるようにする。ジョブがある間は、ウィンドウを閉じても通知領域に常駐して続ける。

さらに、オーナーの依頼で、デプロイに利用可能期限日（既定は今日から 32 日後）を設定し、期限で自動で削除する。デプロイした環境（リソースグループとアプリ名の組）を、URL・パスワード・CPU とメモリ・DB のデータの永続化などとともに、ページング・フィルタ・並べ替えのできる一覧で管理する（6）。

## 3. P1〜P4 の修正（7a）
### 3.1 エラーの表示（P1）
- `Visibility` を関数の結び付けではなく、ViewModel の `bool`（例: `HasError`。`Error` が変わるたびに変更を通知する）で決める。引数が null になる関数の結び付けを使わないため、原因の見込みが外れていても直る
- 同じ作りの表示（`IfText` / `IfNotNull` を使うもの: エラー 6 か所、Dry-run の docker-compose.yml、URL、削除のアプリ名の入力欄）をすべて直す
- UI テスト（CI）: Dry-run で誤った設定で保存してエラーを出し、正しい設定にして保存すると、エラーの領域が消える

### 3.2 状態の確認（P2）
- 環境が無い（`Exists` が false）場合は、永続化の行を出さない（「デプロイされた環境はありません。」だけにする）
- 同じ対象のジョブが実行中・待機中なら、「デプロイ（または削除）を実行中のため、まだ反映されていない場合があります」と添える

### 3.3 処理中の表示（P3）
- 計画（デプロイ・削除）、状態の確認、サブスクリプションの読み込み、Dry-run の保存の各画面に、処理中の表示（`ProgressRing`）と、今している段階の文、経過した秒数を出す
- 段階は Application から知らせる。`DeploymentWorkflow.PlanAsync` / `DeletionWorkflow.PlanAsync` / `DeploymentInspector.InspectAsync` に、省略できる `IProgress<string>`（段階の説明）を足す（CLI・MCP は渡さないので、動きは変わらない）。段階の例:
  | 処理 | 段階 |
  |---|---|
  | デプロイの計画 | リソースグループを確認しています → Container Apps Environment を確認しています → Container Apps を読んでいます → ストレージアカウントを確認しています（永続化する場合） → 権限を確認しています |
  | 削除の計画 | リソースグループを確認しています → 削除の対象を読んでいます → ストレージアカウントを確認しています |
  | 状態の確認 | リソースグループ → Environment → Container Apps → ストレージアカウント |
  | サブスクリプションの読み込み | テナントの一覧を読んでいます → テナント n / m（名前）のサブスクリプションを読んでいます |
- 実行中のジョブは、今と同じく手順（「2 / 4: …」）と進み具合のバーを出す。7b の帯（4.4）で、どの画面からも分かるようにする

### 3.4 デプロイ・削除の画面のジョブ（P4）
- デプロイの画面には、その対象の直近のデプロイのジョブだけを、削除の画面には直近の削除のジョブだけを出す（7b ではジョブの一覧から選んだものを詳しく出す）
- 「Timetracker を開く」は、直近のデプロイが成功して URL がある場合だけ押せる。ジョブが変わるたびに押せるかを更新する

## 4. ジョブの順番待ち・予定・停止（7b）
### 4.1 ジョブの状態
| 状態 | 意味 | できる操作 |
|---|---|---|
| 予定 | 指定の時刻まで待つ | 取り消し、一時停止、時刻の変更 |
| 待機中 | 同時実行の上限に達しているため、順番を待つ | 取り消し、一時停止 |
| 一時停止 | 利用者が止めた（予定・待機中から）。再開するまで実行しない | 再開（予定の時刻を過ぎていれば待機中になる）、取り消し |
| 実行中 | Azure を操作している | 停止（今の手順の後で止める） |
| 停止中 | 停止を受け付け、今の手順が終わるのを待っている | なし |
| 完了 / 失敗 / 取り消し / 停止 | 終わった | 詳細の表示、記録から消す |

### 4.2 登録
- 計画 → 確認（今と同じ）の後、「今すぐ実行」か「予定に追加（日時）」を選ぶ。今すぐ実行でも、同時実行の上限に達していれば待機中になる
- 同じ対象（サブスクリプション・リソースグループ・アプリ名）のジョブが予定・待機中・一時停止・実行中・停止中なら、その対象は計画も登録もできない（D2。画面に「この対象のジョブ（予定 10:30）があるため、計画できません」などと出す）
- 計画の有効期限（15 分）より後に実行するジョブは、実行の直前に計画し直し、利用者が確かめた計画と比べる（操作の一覧、データ消失の同意が要るか、ブロッカー、作るストレージアカウント）。違えば実行せずに失敗にし、理由（何が変わったか）を出す。同じ対象のジョブは登録させないため、違いは本ツールの外での変更か、別の PC・CLI・MCP からの操作による
- デプロイのジョブはパスワードを含む設定を持つ。アプリの中（メモリ）だけに持ち、保存しない

### 4.3 実行
- 対象が違うジョブは同時に実行する。同時に実行する数の上限は既定 2（「設定」で 1〜4。この値はアプリのデータに保存する）（D1）
- 予定の時刻を過ぎたもの・待機中のものから、登録の順に始める
- 停止（D4）: ジョブの各手順の境目（`JobContext.ReportStep`）で停止の要求を確かめ、要求があれば次の手順に進まずに「停止」で終える。今の手順（例: Environment の作成。10 分前後かかる）は止めない。作りかけのリソースは残り、もう一度実行すると続きから処理する（デプロイは冪等）。削除で止めた場合も、もう一度削除すれば続きから消す
- Application の変更: `JobContext` に停止の要求（`StopRequested`）と、`JobStatus.Stopped` を足す。MCP は停止を要求しないため、MCP のジョブは今と同じ（`get_job_status` の状態に `stopped` が出ることはない）

### 4.4 画面
- 「実行の記録」を「ジョブ」に改め、すべてのジョブを新しい順に一覧にする（種別と対象、状態（予定の時刻を含む）、手順、遅れの注意、ログと結果、操作のボタン（取り消し・一時停止・再開・停止・予定の変更））。終わったジョブは「終わったジョブを一覧から消す」で消せる（7b の実装では、経過時間は出さず、各ジョブのログの時刻で分かるようにした。選んだジョブだけを詳しく出す形にはせず、各ジョブにログと結果を出す）
- 「デプロイ」「削除」の画面の実行のボタンを「今すぐ実行」「今すぐ削除」とし、その下に予定の日付・時刻と「予定に追加」を置く（既定は今から 1 時間後）
- どの画面にも、上部に帯を出す（例: 「実行中 1・待機中 1・予定 2」。押すとジョブの画面に移る）
- 実行中でも、別の対象の計画・登録、状態の確認、Dry-run はできる

### 4.5 Azure へのサインイン
- 予定の時刻にトークンの取得で対話（MFA など）が要る場合は、WAM のサインインの画面が出る。サインインしないまま一定時間（10 分）が過ぎたら、そのジョブは失敗にし、通知する（ほかのジョブは続ける）

## 5. 通知領域への常駐（7c）
- ジョブ（予定・待機中・一時停止・実行中・停止中）があるときにウィンドウを閉じると、アプリを終了せず、ウィンドウを隠して通知領域にアイコンを出す（D3。オーナーの提案）。初めて隠したときに「バックグラウンドで実行を続けています」と通知する
- 通知領域のアイコンのメニュー: 「開く」「終了」。「終了」は、ジョブが残っていれば確認する（実行中のジョブは止まり、作りかけのリソースが残る。予定・待機中のジョブは消える）
- ジョブが終わる（完了・失敗・停止）たびに通知し、通知を押すとそのジョブを開く（Windows App SDK の `AppNotificationManager`）
- ジョブが無いときにウィンドウを閉じると、今と同じく終了する
- 制約（画面と手順書に書く）: Windows のサインアウト・再起動・シャットダウンではアプリが終わり、残ったジョブは消える。PC がスリープしている間は実行しない（予定の時刻を過ぎていたら、動けるようになったときにすぐ実行する。D14）
- 通知領域のアイコンは、WinUI 3 と Windows App SDK に API が無いため、Win32 の `Shell_NotifyIcon` を使う。OSS の H.NotifyIcon.WinUI（2.4.1）を使う（D15）

## 6. 利用可能期限とデプロイの一覧（7d）
### 6.1 利用可能期限日
- 「設定」に「利用可能期限日」を加える。選べるのは「既定」（新しくデプロイする場合は今日から 32 日後、再デプロイは今の期限を引き継ぐ。D9・D11）、日付の指定、「期限なし」（D12）。画面には、既定で決まる日付も表示する。今日より前の日付は誤りにする
- 期限は、期限日の終わり（その日の 23:59:59、利用者の PC の時刻帯）とする（D17）。タグには UTC の時刻（ISO 8601）で記録する
- 記録する場所（D5）: 本ツールで作るリソース（Container Apps Environment・3 つの Container App・ストレージアカウント）のタグ。リソースグループは本ツールのものと限らない（既存のものを使える）ため、タグを付けない
  | タグ | 値 | 付けるとき |
  |---|---|---|
  | `tt-deployed-at` | 最後にデプロイした時刻（UTC、ISO 8601） | デプロイのたび |
  | `tt-expires-at` | 利用可能期限（UTC、ISO 8601）。期限なしは `none` | デプロイのたび（省略した再デプロイは今の値のまま）・期限を変えたとき |
- 再デプロイで期限を指定しなければ、今の `tt-expires-at`（`none` を含む）を引き継ぐ（D11。今の管理タグの引き継ぎ `ManagedTags.Merge` と同じ）。タグが無い（この機能より前にデプロイした）環境の再デプロイでは、32 日後にする
- CLI・MCP サーバーでも指定できる（D10）: CLI は `--expires-on <yyyy-MM-dd | none>`、MCP の `plan_deployment` は `expires_on`。省略時はデスクトップアプリと同じ（新しくデプロイする場合は 32 日後、再デプロイは引き継ぐ）。CLI・MCP には期限での削除の仕組みが無く、削除はデスクトップアプリが行う。この動きの変化（省略すると 32 日後に削除の対象になる）を README・MCP の説明（instructions・Resources）・計画の表示と結果に書く。CLI・MCP の期限日は、それぞれが動く PC・サーバーの時刻帯で期限日の終わりとする
- 計画の画面と結果に、期限日と「期限の後に自動で削除します（DB のデータも消えます）」を出す

### 6.2 期限の前の通知と、期限での削除
- アプリは、起動したとき・サインインしたとき・その後 30 分ごとに、デプロイの一覧（6.3）を読み、期限が近いもの・過ぎたものを探す
- 期限の 3 日前と前日に通知する（D7）。同じ通知を何度も出さないよう、出した通知（デプロイの ID と種類）をアプリのデータに記録する（パスワードなどは含まない。正は Azure のタグで、この記録は通知の重複を防ぐためだけに使う）。通知と一覧から、期限を延ばせる（タグを書き換える）
- 期限を過ぎたものは、確認なしで削除のジョブを登録する（D7。7b のジョブの仕組みを使い、同時実行の上限と、同じ対象のジョブを登録させない決まりに従う）。削除の直前に計画し直し、本ツールで作ったもの（管理タグがあるもの）だけを消す。期限での削除は、DB のデータ（ストレージアカウント）も消す（`--keep-db-data` を使わない）。デプロイのときに本ツールが作ったリソースグループ（`managed-by` のタグがある）は、空になればリソースグループも削除する（`resource-group-deletion.md` の Q4）
- 削除の前に、`tt-expires-at` を Azure から読み直す。別の PC や一覧で期限が延ばされていれば削除しない
- 複数の PC のアプリが同時に削除しようとしても、削除は冪等（既に無いものは「既に無い」として続ける）なので害は無い
- サインインしたアカウントに権限が無いサブスクリプションの期限切れは削除できない。一覧に「権限が無いため削除できません」と出し、通知する
- 確実に削除できるよう、Windows のサインイン時に、ウィンドウを出さずに通知領域で起動できるようにする（MSIX の `StartupTask`。D16）。どの PC でもアプリが動いていなければ、次にどれかの PC で動いたときに削除する（削除が遅れる）。この制約は画面と手順書に書く

### 6.3 デプロイの一覧
- 集め方（D8）: Azure Resource Graph（`Azure.ResourceManager.ResourceGraph` の `GetResourcesAsync`）で、サインインしたアカウントが読めるすべてのサブスクリプションから、管理タグ（`managed-by` が `ttdeploytool`、または以前の値）の付いた Container Apps Environment と Container App・ストレージアカウントを 1 回の問い合わせで読み、リソースグループとアプリ名（`tt-app-name`）の組ごとにまとめる。別の PC・CLI・MCP サーバーでデプロイしたものも出る
- 一覧の列: サブスクリプション（名前）、リソースグループ、アプリ名、URL（押すとブラウザーで開く）、デプロイ日（`tt-deployed-at`）、利用可能期限日（`tt-expires-at`。期限が近い・過ぎたものは色を変える）、DB 種別、DB のデータの永続化、Timetracker・DB・Redis の CPU とメモリ、状態
- パスワード（D6）: 一覧には出さず、行の「パスワードを表示」を押したときだけ、その環境の Container App のシークレット（DB のパスワード・Timetracker のパスワード）を Azure から読む（Container Apps の listSecrets。`ContainerAppResource.GetSecretsAsync`）。伏せ字で表示し、コピーできる。PC には保存しない（`desktop-app.md` の Q4 を変えない）。読むには `Microsoft.App/containerApps/listSecrets/action` の権限（Contributor など）が要る。権限が無ければ、その旨を表示する。読んだことは診断用のログに書く（値は書かない）
- フィルタ: サブスクリプション（名前・ID の中間一致）、リソースグループ名（中間一致）、デプロイ日（範囲）、利用可能期限日（範囲・「期限なし」・「7 日以内」）
- 並べ替え: サブスクリプション、リソースグループ、デプロイ日、利用可能期限日（昇順・降順）
- ページング: 1 ページの件数を 20 / 50 / 100 から選ぶ。前・次のページ、全件数を出す。フィルタ・並べ替え・ページングは、読んだ結果に対してアプリの中で行う（管理タグの付いたものだけを読むため、件数は多くても数百と見込む。Resource Graph の 1 回の応答の上限 1,000 件を超える場合は、続きのページ（`$skipToken`）を読む）
- 行の操作: 状態の確認、期限の変更、削除（計画 → アプリ名の入力 → 実行。今の削除の画面と同じ）、この対象を「サインインと対象」に入れる（再デプロイのため）
- Resource Graph の反映の遅れ: デプロイ・削除の直後は、Resource Graph に反映されるまで数分かかることがある。このアプリのジョブで作った・消したものは、ジョブの結果で一覧を補う
- 一覧の読み込みにも、処理中の表示（3.3）を出す
